# Q4. Devinユーザに必要な知識・経験は？（必須 / 推奨）

📚 [トップ索引](../../README.md) ｜ [カテゴリ索引: Devin入門（What/Who）](README.md)

---

> **メタ**: 最終確認日 2026/4/16 ｜ 根拠 運用観察ベース ｜ 推定なし

### 結論: **必須は「GitHub操作・仕様の言語化・レビュー能力」の3つ**。**推奨は「CI/CD・DB・クラウド・ドメイン知識」等**。経験年数より**「自分が何を作りたいか言語化できるか」**が決定的

### 必須スキル（これがないとDevinを実用運用できない）

### 1. SCM（GitHub等）の基本操作 ⭐必須

| 項目 | なぜ必須か |
|---|---|
| **GitHubアカウントを持っている** | DevinのSCM連携前提 |
| **リポジトリ・ブランチ・PRの概念** | Devinの成果物受け取り方 |
| **PRレビュー操作**（comment/approve/request changes） | Devinの出力を受け止める手段 |
| **マージとconflict対処の基本** | Devinが出したPRを本線に取り込む作業 |
| **issue/task管理** | タスクの起点 |

→ GitHubを1度も使ったことがない人は、**先に30分〜1時間Git/GitHubチュートリアル**が事実上必須。

### 2. 仕様の言語化能力 ⭐必須

Devinは自然言語で指示するが、**曖昧指示は曖昧結果**を招く。

#### 良い指示の例（言語化できている）
```
Next.jsのルート `/api/users` に GET エンドポイントを追加。
- レスポンス: { id, name, email }[] のJSON
- 認証: Authorization header Bearer必須（既存middleware `verifyToken` を使う）
- DB: prisma の `user` テーブルから最大100件
- テスト: Vitestで200/401/500のケースを追加
```

#### 悪い指示の例（言語化できていない）
```
ユーザAPI作って。良い感じに。
```

→ **要件を箇条書きにできるレベル**は最低限必要。

### 3. レビュー能力 ⭐必須

- Devinの出力を**鵜呑みにしない**
- コードを読んで**妥当性判断**できる
- テストが**実際に機能要件をカバーしているか**判断できる
- **セキュリティ問題**に気づける最低限の感度

### 4. 最低限のコード読解 ⭐必須（非SEでも）

- 生成された変数名・関数名が**意味をなしているか**
- **プロジェクトの既存パターン**に合っているか
- 明らかにおかしい箇所を**指摘できる**

→ 非SEでも、出力の良し悪しを判定する最低限の読解は必要。

### 推奨スキル（あった方が格段に効果的）

### 技術系

| スキル | 理由 |
|---|---|
| **CLI / シェルの基本** | Devinセッションのシェル操作理解、エラー読解 |
| **1つ以上のプログラミング言語の基礎** | 出力コードの妥当性判断 |
| **CI/CDの概念**（GitHub Actions等） | Devinが触るCI理解、パス/失敗の判断 |
| **DB基礎**（SQL / schema） | データ系タスクで必須級 |
| **クラウド基礎**（AWS/GCP/Azure） | デプロイ・インフラタスクで重要 |
| **Dockerの基礎** | 環境構築・再現性 |
| **テストの概念**（単体/結合/E2E） | Devinにテスト追加を頼むときに効く |
| **API設計の基礎**（REST/GraphQL） | バックエンドタスク |
| **セキュリティ基礎**（OWASP Top 10） | レビュー・Bug Catcher理解 |

### ドメイン系

| スキル | 理由 |
|---|---|
| **ビジネス要件の理解** | 正しい指示を出すのに必要 |
| **UX/UI感度** | フロントエンドタスクで品質差が出る |
| **ユーザの業務知識** | 業務自動化タスクで必須 |

### ソフトスキル系

| スキル | 理由 |
|---|---|
| **ドキュメント読解** | Devin docs・AGENTS.md・Knowledge整備 |
| **英語の読解** | docs・エラー・OSS issueで英語頻出 |
| **実験マインド** | AIは試行錯誤で育てる性質 |
| **タスク分解力** | 大きな仕事を小さく切って渡す |

### 経験年数の目安（あくまで目安）

| 経験 | Devinでの使い勝手 |
|---|---|
| **プログラミング未経験** | 定型自動化・資料生成・学習補助に限定、出力検証は困難 |
| **独学数ヶ月〜1年** | 個人プロジェクト・学習用途、PR単位の小さな作業可 |
| **SWE 1〜3年** | 日常業務の雑務委任、並列タスクで工数削減 |
| **SWE 3〜7年** | **最大ROI**、設計・レビューに集中、Devinが雑務担当 |
| **SWE 7年以上 / テックリード** | **Devin運用設計者**、AGENTS.md/Playbook整備、組織展開 |

### スキルギャップの補い方

### ケース1: GitHubを使ったことがない
- 1時間の公式チュートリアル（GitHub Docs / Progate等）で十分
- リポジトリ作成 → ファイル編集 → commit → PRの基本フロー体験

### ケース2: プログラミングが全くできない
- **ChatGPT/Claude等で基礎を学びながら**Devinを使うのが現実的
- 最初は**Devin公式のサンプルタスク**で感覚を掴む
- 徐々にドメインを広げる

### ケース3: CI/CDを知らない
- 最初はCIなしの小さなリポで練習
- Devinに「CIを追加して」と頼むこともできる
- **GitHub Actions公式docs**を1時間で読める

### ケース4: 英語が苦手
- Devinへの指示は日本語でOK
- ただし**エラーメッセージやOSS docsは英語**が多い → 自動翻訳併用

### 「スキル不足で困る」典型シーン

| シーン | 原因スキル | 対処 |
|---|---|---|
| Devinのエラーが読めない | CLI/シェル基礎 | 基本コマンド（cd/ls/grep/git）を覚える |
| DB変更で本番壊れた | DB/SQL基礎 | 最低限のSQL学習、ステージング環境で試す |
| セキュリティ問題に気づかない | OWASP基礎 | Devin Reviewを併用、Bug Catcher活用 |
| PRレビューで何を見ればいいか分からない | コード読解・テスト概念 | Devin Reviewに一次レビューさせて、論点を見る |
| Devinが何度も同じ失敗をする | 仕様言語化 | 要件を書き出してPlaybook化 |

### 業務別の必要スキル

### Webアプリ開発
- 必須: HTML/CSS/JS, HTTP, REST, DB基礎, GitHub
- 推奨: フレームワーク1つ(React/Vue/Next), テスト, CI/CD

### モバイル開発
- 必須: Swift/Kotlin or Flutter/RNの基礎, GitHub
- 推奨: AppStore/PlayStore提出, 実機テスト

### データサイエンス
- 必須: Python, pandas/numpy, SQL, Jupyter
- 推奨: 機械学習基礎, 統計, 可視化

### DevOps/SRE
- 必須: Linux/CLI, Docker, IaC(Terraform/Ansible), クラウド
- 推奨: K8s, 監視(Prometheus等), ログ解析

### 業務自動化（非SE向け）
- 必須: Excel/CSV操作感, 簡単なスクリプト読解, GitHub(最低限)
- 推奨: Python基礎, API概念, 認証トークン扱い

### まとめ

| 必要度 | スキル |
|---|---|
| **必須（これがないと運用不可）** | **GitHub操作 / 仕様の言語化 / レビュー能力 / 最低限のコード読解** |
| **強く推奨** | **CLI / 1言語の基礎 / CI/CD / DB / テスト概念** |
| **推奨（あると効率UP）** | **クラウド / Docker / API設計 / セキュリティ基礎 / 英語読解** |
| **ドメイン依存** | **業務知識・UX感度・ユーザ理解** |
| **経験年数** | **3〜7年が最大ROI**、未経験でも限定用途なら可 |

**核心**: Devinは「**仕様を言語化できて、出力をレビューできる人**」が最大効果を得る。**GitHub操作と仕様言語化が最低ライン**、他はやりながら身につける。経験年数より、**「自分がやりたいことを言葉にできる」「出力の妥当性を判定できる」の2つが決定的**な分水嶺。

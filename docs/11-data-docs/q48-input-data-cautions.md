# Q48. Devinに入力するデータで気をつけることは？（APIキー・個人情報・機微情報）

📚 [トップ索引](../../README.md) ｜ [カテゴリ索引: データ入出力・ドキュメント理解](README.md)

---

> **メタ**: 最終確認日 2026/4/16 ｜ 根拠 https://docs.devin.ai/enterprise/security ｜ 推定あり

### 結論: **APIキー/パスワード/認証情報は絶対にチャット/コードに直書きしない → Secretsを使う**。**個人情報は最小限に**。**機微情報はEnterprise契約＋Dedicated SaaS/オンプレ**で保護。**平文で入れたデータは履歴に残る前提**

### 絶対にしてはいけないこと

### ❌ NG事例

#### NG-1: APIキーをチャットに貼る
```
チャット: 「OPENAI_API_KEY=sk-proj-abc123... を使って実装して」
```
→ セッション履歴に残る、スクリーンショットで流出の恐れ

#### NG-2: DB接続文字列をコードに書く
```python
# 絶対ダメ
conn = psycopg2.connect("postgres://user:password@prod.db/mydb")
```

#### NG-3: 秘密鍵ファイルをそのまま添付
```
ssh-key.pem を添付
```

#### NG-4: 本番DBのダンプをそのまま渡す
```
production_dump.sql（個人情報全部入り）を添付
```

#### NG-5: 顧客データを何の匿名化もなく渡す
```
user_list.csv（氏名・住所・電話番号・クレカ番号）を添付
```

### 正しいやり方

### ✅ 推奨1: Secretsで秘匿情報を管理

**手順**:
1. Webapp → Settings → Secretsへ
2. 秘密値を登録（例: `OPENAI_API_KEY` = `sk-proj-...`）
3. セッションでは**環境変数として自動注入**される
4. コードは `os.getenv("OPENAI_API_KEY")` のみ

**詳細**: Q15, Q31参照

### ✅ 推奨2: 機微データを事前に匿名化/マスキング

```python
# アップロード前にローカルで処理
import pandas as pd
import hashlib
import secrets

df = pd.read_csv("original.csv")
df["phone"] = "***-****-****"  # 電話番号マスク

# セッション毎に salt を生成（再同定攻撃を抑制）
salt = secrets.token_hex(16)
def anonymize_email(e: str) -> str:
    return hashlib.sha256(f"{salt}:{e}".encode()).hexdigest()[:16]
df["email"] = df["email"].apply(anonymize_email)

df["name"] = "anonymized"
df.to_csv("safe.csv")  # これをDevinにアップロード
```

> ⚠️ **ハッシュ化は匿名化ではない**。入力空間が小さい（メールアドレス・電話番号・氏名等）フィールドは、辞書攻撃で再同定できる。上記のように**ランダム salt を付ける**か、**マスキング（`***`）／ダミー置換**を優先するのが安全。GDPR等の法令上の「匿名化」に到達するにはさらに k-匿名性等の評価が必要。
>
> - Python の組込 `hash()` は**プロセス毎にランダム化**され再現性がないうえ、戻り値が `int` のため `hash(e)[:8]` は `TypeError: 'int' object is not subscriptable` になる。必ず `hashlib` を使うこと。

### ✅ 推奨3: ダミーデータで設計 → 本番は別環境で適用

- Devinセッションでは**合成データ・ダミーデータ**で開発
- 本番DB接続・本番データ処理は**ローカル環境 or 本番CI**で実行

### ✅ 推奨4: 最小原則で渡す

- **必要な分だけ**渡す（ファイル全体より該当箇所のみ）
- **カラムは必要分のみ**（列選択してから渡す）
- **期間も限定**（全履歴より直近1ヶ月等）

### データ種別別の注意

### A. APIキー / トークン

| 項目 | 推奨 | NG |
|---|---|---|
| OpenAI/Anthropic等のLLM鍵 | **Secrets** | 直書き |
| GitHub Token | **SCM連携の内部管理** or Secrets | 直書き |
| AWS Access Key/Secret | **Secrets**（`AWS_ACCESS_KEY_ID`等） | 直書き |
| DB接続文字列 | **Secrets** | コードに埋込 |
| Webhook URL（秘密成分あり） | **Secrets** | 直書き |
| JWTトークン | **Secrets（短期間利用）** | 直書き |
| TOTPシード（2FA） | **Secrets（`_2FA_`プレフィックス）** | 直書き |

### B. アカウント / パスワード

- **絶対に平文で渡さない**
- 本番アカウントは**Devin経由で操作させない**（操作ログ的な意味でも問題）
- テスト環境のテスト用アカウントのみ**Secrets経由**で許可

### C. 個人情報（PII）

| データ | 注意 |
|---|---|
| **氏名・住所・電話・メール** | マスキング/匿名化してから渡す、最小限 |
| **クレジットカード番号** | 絶対に渡さない（PCI DSS違反のリスク） |
| **マイナンバー・SSN** | 絶対に渡さない（法令違反のリスク） |
| **パスポート/免許証画像** | 絶対に渡さない |
| **指紋・生体認証データ** | 絶対に渡さない |
| **医療データ** | HIPAA等の規制対象、Enterprise契約必須 |

→ 「**仕事のテスト用なので**」と軽く扱わない。**1件でも本物が混じっていれば問題**。

### D. 企業機密

| データ | 注意 |
|---|---|
| **M&A検討資料・経営情報** | Enterprise契約、Dedicated SaaS前提 |
| **未公開製品仕様** | 同上 |
| **顧客名刺・顧客リスト** | 同上 |
| **契約書** | 署名済みでも個別情報含むので注意 |
| **財務データ（未公開）** | 同上 |
| **特許出願前のアイデア** | 公知化リスク |

### E. ソースコード

| データ | 注意 |
|---|---|
| **OSSライセンスのコード** | 問題なし |
| **会社の独自コード** | 会社の規定次第、通常は業務用Devin契約なら可 |
| **他社のソースコード（委託請負含む）** | 契約上の守秘義務確認必須 |
| **バイナリのみで配布されるコード** | リバースエンジニアリング規約違反のリスク |
| **クローズドソースの依存ライブラリ** | ライセンス確認必須 |

### 公式のデータ処理ポリシー

docs.devin.ai/enterprise/securityより:

> - **デフォルトで学習に使わない**: Cognition does not train models on customer data or code
> - **Enterprise Dedicated SaaS**: 顧客tenantに保存、顧客制御
> - **Web Application**: ユーザが明示的に提供したデータのみ処理
> - **SOC 2 Type II認証済**（取得時期は Trust Center 参照）
> - **転送/保存時暗号化**

→ **平均的なセキュリティ水準は高い**が、**「学習に使われない」≠「保管されない」**。契約期間中は保管される。

### 入力時のチェックリスト

実務で使える自問自答:

```
□ この情報に秘密成分（鍵・パスワード）は含まれないか？
  → 含まれる → Secretsで

□ 個人情報（氏名・連絡先・ID）は含まれないか？
  → 含まれる → 匿名化してから

□ 会社の守秘義務に触れないか？
  → 触れる可能性 → 上長/法務に確認、Enterpriseで

□ 顧客との契約で「第三者サービスに渡してはいけない」とされていないか？
  → 制限あり → 渡さない or 許可取る

□ 最小限の情報に絞れているか？
  → No → 絞る（不要な列・期間を削除）

□ 後で削除要求が来たときに対応できるか？
  → 削除フロー未確認 → 事前に Q51 確認
```

### ユーザ側のデータ保護 Best Practice

### 1. 個人/個人事業主
- **Secretsの活用**
- **匿名化ツール**（faker等）で合成データに変換
- **GitHub private repoでテスト**

### 2. スタートアップ
- **会社の情報セキュリティポリシー策定**（Devin利用規定）
- **Teamsプラン**で組織管理
- **Secretsをチームで共有**（個別保持より管理容易）

### 3. 中堅〜大企業
- **Enterprise契約 + Dedicated SaaS**
- **自社VPC内で稼働**
- **監査ログ有効化**
- **PII検出ツール**（Presidio等）を事前フィルタに
- **社内DLP（Data Loss Prevention）**との統合

### 4. 規制業種（医療・金融・公共）
- **規制準拠（HIPAA / PCI / GDPR / 個人情報保護法）の確認**
- **Dedicated SaaS または OSS代替（OpenHands）**のセルフホスト検討
- **データ処理契約（DPA）締結**
- **データマスキング/トークナイゼーション必須**

### データが残る場所

| 場所 | 内容 | 保持期間 |
|---|---|---|
| **セッションチャット履歴** | 会話・添付 | 契約期間中 |
| **セッションVM** | 生成ファイル | セッション終了後に一定期間 |
| **Playbook/Knowledge** | 明示的に登録したもの | ユーザ削除まで |
| **Secrets** | 秘密値 | ユーザ削除まで |
| **CognitionのAWS S3等** | アップロードファイル | 契約ポリシー次第 |

→ **「一度入れたら消えない」前提で臨む**のが安全。

### 事故事例（一般論）

### 事例1: .envファイル丸ごとアップロード
- 症状: `.env`に本番APIキーが入っていた
- 影響: API鍵ローテーション必要、ログ調査
- 対処: `.gitignore`同等の「アップロード前チェック」習慣

### 事例2: スクリーンショットにパスワード映り込み
- 症状: ブラウザのパスワードマネージャが展開された状態で共有
- 対処: スクショ前にマスキング、クリーンなテストデータ画面を使う

### 事例3: 顧客データのサンプルを匿名化せず投入
- 症状: 実顧客の氏名・連絡先を含むCSVをそのままアップロード
- 対処: 法的報告義務の可能性、社内インシデント対応
- 予防: **匿名化スクリプト**を事前に用意、**DLPツール**で自動検出

### 万が一入れてしまった時の対応

1. **即座に使用停止**（セッション削除）
2. **関連する秘密（APIキー等）をローテーション**
3. **ログの確認**（誰に共有されたか）
4. **Cognitionサポートに削除依頼**（Q51参照）
5. **社内インシデント報告**（規定次第）
6. **関係者通知**（顧客情報なら個人情報保護法に基づく通知義務）

### まとめ

| カテゴリ | 鉄則 |
|---|---|
| **APIキー/トークン** | **必ずSecrets**、平文厳禁 |
| **パスワード** | **Secrets** + 本番アカウント操作させない |
| **個人情報** | **匿名化**してから、最小限、クレカ/マイナンバー/医療は絶対NG |
| **企業機密** | **Enterprise + Dedicated SaaS**、契約・法務確認 |
| **コード** | **OSSはOK**、**独自・委託は規約確認** |
| **事前チェック** | **.env混入・スクショ映り込み・実データ混入**を常にチェック |
| **事後対応** | **鍵ローテーション / 削除依頼 / 社内報告** |

**核心**: Devinのセキュリティ水準は高いが、**「入れたデータは保管される前提」**が鉄則。**秘密はSecrets**、**個人情報は匿名化**、**機微情報はEnterprise契約**、**最小原則**の4つを守れば事故は大半防げる。万が一混入したら**即削除依頼＋鍵ローテーション**。
